## Original research notes

The source examines whether memory-tiering software actually removes hardware barriers, making it relevant to the gap between loading a model and completing useful work.

- [1:19](https://www.youtube.com/watch?v=qW2E2ay47dw&t=79s): The presenter argues that system memory, storage and CPU behavior become important after reducing the graphics-memory requirement. The bottleneck may move rather than disappear.
- [6:52](https://www.youtube.com/watch?v=qW2E2ay47dw&t=412s): Different memory tiers are described as having different access costs. An advisor should represent where model data resides, not merely sum all available storage and memory capacity.
- [12:16](https://www.youtube.com/watch?v=qW2E2ay47dw&t=736s): An owner report describes difficulty during long workloads that move experts into system memory. This is attributed community evidence, not an independently reproduced stability measurement.
- [18:15](https://www.youtube.com/watch?v=qW2E2ay47dw&t=1095s): The discussion compares total time for an iterative task rather than only generation speed. Multiple agent steps can amplify a latency difference that looks modest in isolated responses.
- [23:59](https://www.youtube.com/watch?v=qW2E2ay47dw&t=1439s): The presenter notes limited evidence when comparing compressed local execution with an API. A small question sample cannot establish general equivalence for production decisions.

**Platform implication.** For the platform, make memory tier, cold-start cost, task completion time and compression explicit. Avoid promising that a low-VRAM runtime makes hardware irrelevant, or that one owner's successful run establishes a broadly reliable deployment.
