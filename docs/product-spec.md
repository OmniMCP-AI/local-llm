# fastest.ai product specification

## Problem Statement

People choosing a local AI setup need to know whether their current machine can handle a real workload, how long they will wait, and whether buying hardware beats using a cloud service. Specifications, vendor benchmarks, offer prices, and community test results are dispersed, change frequently, and often omit the exact artifact, hardware configuration, runtime, or test conditions. The same uncertainty affects external AI agents that answer purchasing and deployment questions.

Local.ai already compares exact model variants, hardware, inference engines, harnesses, and runtime settings using quality, task time, and cost. Our target is a richer decision experience for specific workloads, with regional purchasing data, visible failures and uncertainty, reproducible evidence, and the same answers available to external agents. Competitive evaluation is limited to observed public behavior and representative user tasks. [local.ai methodology](https://local.ai/about)

## Solution

Start with one decision for a Chinese-speaking marketing or e-commerce team. Given a consented text task, a known machine, a monthly volume and an acceptable wait, show three choices side by side: keep the machine, use a cloud endpoint, or upgrade. Each choice shows task quality, time, cost range, deployment and privacy constraints, evidence, and what still needs a test. A separate fixed ComfyUI product-image workflow tests whether the same decision process works for images.

Build out from that case. A source-linked catalog supports browsing even where measurements are sparse. A visitor can start with a machine, a budget or an expert comparison, follow machine and model profiles in either direction, and inspect the exact run. Pinned llmfit supplies fit estimates. Reviewed runs supply measurements. PostgreSQL releases supply Markdown, the Graphify wiki, HTML, charts, accessible tables and, in a later milestone, read-only agent access. Reviewed releases also supply daily editorial packages.

## Implementation Decisions

The [local data and catalog expansion](catalog-expansion-spec.md) adds a reproducible local ER import, a profile for every GPU identity, and curated popular and small-model discovery. The existing M1 tickets cover import and catalog delivery, with recurring retail collection in M3.

### Start with the hardware and model catalog

- The first release must give people a searchable, paginated list of **graphics cards, machine profiles, and models**. Define the covered source list and snapshot date upfront. Reconcile every eligible entry from the pinned llmfit hardware/model inputs and approved vendor or research sources, and show source coverage, import counts, and unsupported or missing records. Source-complete means all eligible records in the named snapshots. It does not mean every machine someone could assemble.
- Keep cards and machines distinct. A card entry has manufacturer, board or product family, memory pool and source alias. A machine profile has a versioned configuration or factory preset, BOM and benchmark status. Preserve documented partial profiles and keep them out of matched rankings until they have the required conditions. Map and deduplicate aliases before linking records. Add new vendor or machine sources incrementally, including NVIDIA, AMD, Intel and Apple where the relevant catalog and rights exist.
- A model entry links to the official Hugging Face repository or GitHub source and can list exact artifacts and revisions when available. Carry source, license metadata and catalog vintage. Keep missing or unverified links visible and under review. Never infer artifact fit or benchmark availability from catalog membership. Each record resolves to a stable catalog detail or an explicit coverage note. Benchmark pages can grow around the same IDs as evidence arrives.

- Give the Models directory a familiar Hugging Face-style information architecture: a searchable `owner/model` list, visible result count, source-reported tags for parameters, task, format, or license when known, filters and stable pagination, and source-linked Markdown model cards with evidence sections. Distinguish upstream model metadata from fastest.ai-specific fit, runtime support and benchmarks. Mark missing fields instead of inferring them. [Hugging Face Models](https://huggingface.co/models), [Model cards](https://huggingface.co/docs/hub/model-cards)

### Inference runtimes and card-specific techniques

- Start a linked runtime directory with **llama.cpp**, **SGLang**, and **vLLM**. Add related engines and runners as their evidence warrants, with official repository, docs, release or commit, supported workload and artifact formats, and backend/platform scope. Link known support or gaps back to GPU, machine, model/artifact and benchmark pages. A runtime listed in the catalog does not guarantee that a particular card/model combination works. [llama.cpp](https://github.com/ggml-org/llama.cpp), [SGLang](https://github.com/sgl-project/sglang), [vLLM](https://github.com/vllm-project/vllm)
- Maintain a release and tuning watch over authorized upstream repositories, changelogs, issues, and contributor submissions. Start with practical techniques such as GPU offload, context and KV-cache settings, continuous batching, quantized kernels, multi-GPU layout, driver-specific options, and card-family or virtualization workarounds such as reported GPU unlock techniques. Capture the exact hardware, variant, OS/driver, runtime build, flags, workload, prerequisites, limits and failure modes. Store a baseline and tuned measurement separately when a matched retest exists, with differences in speed, memory, task quality, power or stability visible. Label each note upstream documented, fastest.ai verified, contributor reported, unsupported, or unresolved; never imply applicability to a different card generation.
- Join tuning notes to evidence by stable runtime, hardware and workload IDs. Newly discovered claims stay in review, and appear in rankings or recommendations only when a comparable test supports them. Treat submitted patches/scripts as references during intake; any technical reproduction runs in an explicitly authorized benchmark environment. Show current and superseded applicability by version, and link corrections back to the relevant Wiki pages and release snapshots.

Keep the GPU-UNLOCK performance claim in video note 014 separate from similarly named vGPU virtualization projects. Record identity and before/after evidence before attributing a gain.

### Use llmfit directly and preserve its contracts

- Start with upstream commit 26450cccaf3a3f14b1822875f2473847a744a718, workspace version 1.1.20. Build a small, pinned Rust adapter against **llmfit-core** and call its fit analysis from the site's normal request path. This is a required runtime component. Import the pinned, rights-cleared upstream model catalog and hardware calibrations, fixtures, and profiles as applicable. Keep full MIT notice, source commit, upstream item identifier, payload hash, and mapper version. A catalog entry is separate from the model weights and any external benchmark data. [Upstream README](https://github.com/AlexsJones/llmfit/blob/26450cccaf3a3f14b1822875f2473847a744a718/README.md), [MIT license](https://github.com/AlexsJones/llmfit/blob/26450cccaf3a3f14b1822875f2473847a744a718/LICENSE)
- Construct the adapter's SystemSpecs and calculation settings from the visitor's selected configuration or consented input. Pin runtime, context, memory reservations, and estimation inputs, including the provenance for bandwidth assumptions. The upstream CLI's profile mode overlays detected hosts, and its default measured-results enrichment can load third-party cache data. The public fit path uses pure core analysis without those enrichments and must be independent of the app server's hardware. If required inputs are unavailable, return the supported subset or an explicit insufficient-input result. [Upstream hardware behavior](https://github.com/AlexsJones/llmfit/blob/26450cccaf3a3f14b1822875f2473847a744a718/llmfit-core/src/hardware.rs), [Fit analysis](https://github.com/AlexsJones/llmfit/blob/26450cccaf3a3f14b1822875f2473847a744a718/llmfit-core/src/fit.rs), [Measurement enrichment](https://github.com/AlexsJones/llmfit/blob/26450cccaf3a3f14b1822875f2473847a744a718/llmfit-core/src/analysis.rs)
- Store fit results separately from evidence. Preserve native fit level, run mode, suggested quantization, memory, estimated usable context, and nullable speed or latency with the engine revision and assumptions. Label each value by its actual origin. Join eligible contributed aggregates through the site's evidence layer. Keep the upstream model weight license and original HF link, and carry the complete MIT notice on eligible llmfit imports. Merged community submissions retain their contributor source. Family-strength heuristics and older rubric baselines have their own versions. The bundled third-party LocalMaxxing cache requires a separate permission decision for bulk republication.
- Support four versioned contract shapes at the boundary. **HardwareProfile** uses the upstream snake_case schema with complete required fields; BOM, provenance, partial hardware details, and discrete VRAM live in site records outside that native object. **LlmModel** uses the upstream catalog contract for eligible complete rows; a partial source reference cannot acquire a default format, known quantization, or guessed RAM. **BenchmarkEntry / HardwareInfo** use upstream camelCase Rust serialization, with permissive fields requiring site validation and complete metrics preserved in extensions. **Community submissions** use their own schema and require the original submission/run summary; no synthetic submission or trial samples. Handle missing and null as specified by each contract and report unsupported values. [Upstream hardware schema](https://github.com/AlexsJones/llmfit/blob/26450cccaf3a3f14b1822875f2473847a744a718/llmfit-core/data/hardware/schema.json), [Model catalog schema](https://github.com/AlexsJones/llmfit/blob/26450cccaf3a3f14b1822875f2473847a744a718/llmfit-core/data/schema.json), [Benchmark types](https://github.com/AlexsJones/llmfit/blob/26450cccaf3a3f14b1822875f2473847a744a718/llmfit-core/src/benchmarks.rs), [Community schema](https://github.com/AlexsJones/llmfit/blob/26450cccaf3a3f14b1822875f2473847a744a718/llmfit-core/data/community/schema.json)
- Use the research seed's strict projections and separate research extensions as migration fixtures. Account for 116 hardware profiles, 487 component rows, 99 legacy hardware records, 242 test series, and 450 unique observations, including 293 qualified profile associations and 157 unassigned. The updated seed reports 16 schema-compatible hardware projections, 127 structural BenchmarkEntry projections, 140 partial model references, zero complete LlmModel records, and zero native community submissions. These are migration expectations. Run the pinned upstream loader/deserializer and a representative real fit call before claiming compatibility. Store each seed row once across views, with original identifier, source lexeme, unit, locator, missingness, and review outcome. [Seed compatibility contract](https://github.com/OmniMCP-AI/local-llm/blob/e8202e7dec1634b1529db4c123e7b3bfc2a1072b/docs/Local-AI-Comparison-Platform/YouTube-Local-LLM-Transcripts/llmfit/schema.md), [Seed validation report](https://github.com/OmniMCP-AI/local-llm/blob/e8202e7dec1634b1529db4c123e7b3bfc2a1072b/docs/Local-AI-Comparison-Platform/YouTube-Local-LLM-Transcripts/llmfit/validation-report.json)

### Database → Markdown → HTML, charts and tables

- Treat a reviewed PostgreSQL release as the only numeric input to public publishing. Normalize cards, versioned machine BOMs, models and exact artifacts, runtime releases and tuning profiles, workload protocols, runs, metric definitions and observations, prices, and rights. Use stable entity/version IDs and explicit keys for sample scope, load, units, measurement method, and source. Separate raw reports, estimates, and eligible measured facts; keep unknown, failed, and unsupported outcomes explicit.
- Generate versioned **Markdown** page sources and manifests for catalog and entity pages, comparison views, methods, links, and change notes. Each Markdown document carries page, entity, database release and method IDs, evidence references, and declarative view blocks. A view block identifies the cohort, metrics, filters, axes, sort, and a typed release-pinned data result or read-only query. Human-edited narrative stays reviewable in Markdown. Numeric claims in copy must reference release values; avoid independently maintained chart numbers or manual HTML tables.
- Use one shared presentation dataset per view block to produce accessible **HTML, charts, and exact-value tables**. The renderer checks units, required parameters, comparisons, and current rights. It renders explicit no-data, unsupported and stale states from those same records. Publish Markdown, graph index, charts/tables, and API reads against one release manifest so the same observation and number agree everywhere. Publish a correction as a new release; rights withdrawal must also invalidate the affected public artifacts and caches.
- Graphify maintains the reviewed Markdown navigation, crosslinks, and search index downstream of the database release. It has no authority to synthesize benchmarks or to silently replace typed view results. Start with a thin vertical slice: one hardware profile, one model artifact, one pinned workload, a small measured sample, and a price cohort that generate their Markdown pages and both chart and table from one release.

### Context tags for articles, posts and test records

Every article, blog entry, social or forum post, video note, and first-party test report has a stable source ID, content format, publisher/platform, language, publication date or unknown, an editorial scope sentence, and reviewed use-case tags with locators. Use enough tags to describe independent uses. An unsupported topic stays unassigned. Apply these rules to existing material on import and to future GrokBot drafts and corrections.

**Two scopes.** A publication can discuss coding, retrieval, deployment and cost in the same piece. Each specific case links separately to its test series, observation or run, named task or fixture, and the source passage or timestamp that supports it. Record its evidence class and outcome. Where supplied, pin dataset/rubric and version, inputs and success criterion, model artifact and quantization, machine and topology, runtime, input/output length, cache state, concurrency, repetitions and timing/power boundary. Distinguish local measurements, creator reports, simulations, estimates, proposals and qualitative guidance. A methodology article with no indexed runs remains discoverable.

**Reader interaction.** The Wiki and Methods pages lead to a Research library. Readers can combine source type and discussed use case, then filter by task and measurement dimension on the same observation. They can search model, hardware, runtime, conditions, series or observation ID. Each result gives its source, publication date when available, topic tags, and matching records with a timestamp and the underlying test-series notes. Newest-first sorts undated items last. Title sorting, clear filters and shareable filter URLs work in the standalone prototype. Keep a missing task classification visible.

**Graphify tuning.** Use a versioned domain vocabulary with stable IDs, localized display names and reviewed aliases. Extract declared measurements from structured records. Give article topics, case tasks and measurement dimensions different graph edges. Suggestions from unstructured prose stay scoped to their locator and enter editorial review. Changes to a classifier, alias or prompt receive a version, positive and negative examples, and a replay on unseen sources from relevant formats and languages. ## Testing Decisions

1. **Intake to public release.** Replay a bounded import into review, correction and withdrawal. Check source/native counts, idempotency, out-of-order messages, cross-posts, invalid units, digest changes, partial identities, denied destinations and source outages. An allowed chart, table, Markdown page and export must agree on values, missingness and evidence after each release.
2. **Decision end to end.** Use a matched machine/model pair plus an incompatible artifact, failed run and stale price. Exercise fit, goals, rank/map selection, share-state, source links, and same-task cost arithmetic. Run both workload lanes. Test language and market independently, including saved choices, regional Chinese browser tags, unsupported tags, a conversion with a missing FX rate and Arabic layout. Re-run through the public API and a supported MCP client in M4.
3. **Consumer actions.** Check private feedback acknowledgement, idempotent receipt, local/offline handling, opt-in context and public issue handoff. For distribution, render a known release, approve the exact payload, retry a partial delivery and withdraw a claim. Confirm the final public state and the recorded outcome for each destination.

Use the existing standalone prototype and its source fixtures for interaction checks. Production integration acceptance requires the real adapter and release service. Use recorded inputs for repeatability. Live connector and delivery pilots require the approved source or channel account.

## Out of Scope

- Exhaustive hardware/model matrices, universal scores, private community scraping, mirroring third-party leaderboards or videos, and automatic promotion of scraped claims to benchmark results.
- Training/fine-tuning, broad mobile/edge testing, arbitrary remote execution of uploaded workflows, mandatory local telemetry, autonomous installs or purchasing, and support for every external MCP client.
- Marketplace transactions, trading, and a general-purpose autonomous advisor. Price forecasting and community voting remain research candidates beyond M1–M5. Larger image/video or team benchmarks follow validated demand and available hardware.

- Autonomous public posting without approval, automatic replies or DMs, and full coverage of all channels on day one.
