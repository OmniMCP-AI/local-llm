# LocalDecode catalog, comparisons and market coverage

## Problem Statement

A buyer needs a recognizable photograph of the exact graphics card, a trustworthy price history for their market, and comparisons that explain how a card, build, model or inference engine fits their workload. The baseline catalog had 168 GPU identities and licensed photos on 22 of them. The 88 manufacturer gallery links help identify products and count separately from photos published on a profile. An old benchmark can look current when a site displays only the date of the article that reports it. Inference engines also need a compact comparison that accounts for workload and configuration.

## Solution

Use **localdecode.com** as the public site identity. Build a photo gallery for every GPU card identity, collect eligible used-market observations daily, and show the context and date behind each price and performance claim. Reuse the current PostgreSQL catalog and the same Markdown, HTML, table and chart exports. Extend the build directory and runtime comparisons while keeping short, evidence-linked guidance on all entity profiles.

## User Stories

1. As a buyer, I want a photograph on every graphics card page, so that I can recognize the card I am considering.
2. As a PC builder, I want multiple angles when available, so that I can inspect cooling, connectors, backplate and space requirements.
3. As a shopper, I want the board partner and SKU in the caption, so that I can distinguish different boards that use the same GPU.
4. As a used-card buyer, I want stock and aftermarket boards identified separately, so that a photograph of the stock card cannot establish an advertised modification.
5. As a workstation builder, I want the PCIe, module and regional variants distinguished, so that I can tell what form factor I am seeing.
6. As a reader, I want original source and credit links next to the photo, so that I can inspect its provenance.
7. As a keyboard or mobile user, I want a navigable gallery and descriptive alternative text, so that I can inspect or understand each view.
8. As an editor, I want a photo coverage inventory keyed by exact card, so that I can see which cards still need work.
9. As a researcher, I want to search Wikipedia, Wikimedia Commons, other open collections, manufacturer catalogs, Google Images and Pinterest, so that I can find leads for hard-to-source cards.
10. As an editor, I want to follow search results and Pins back to the original publisher, so that I can review the exact photo and reuse terms.
11. As a photographer, I want my attribution, license and image edits retained, so that republication honors the original grant.
12. As a maintainer, I want to replace or withdraw an image through a versioned release, so that a correction reaches the profile and its exports.
13. As a buyer, I want separate used prices from eBay, Amazon and JD.com where eligible data is available, so that I can compare reasonable offers in my region.
14. As a buyer, I want conditions, currency, dates, seller and shipping basis next to each quote, so that I can judge what it costs to buy.
15. As a shopper, I want asking prices, bids, completed sales and historical references identified separately, so that each point conveys what was observed.
16. As an editor, I want a daily collection record per source and market, so that I can diagnose missing or stale days.
17. As an analyst, I want source observations retained with their origin, publication and capture dates, so that I can tell when the underlying event occurred.
18. As a reader, I want a date marked unknown when the source omits it, so that a later upload never creates a fictitious test or build date.
19. As a shopper, I want a price-versus-performance overview with historical prices below it, so that I can select a GPU or build and inspect its dated quotes.
20. As a shopper, I want a price history for an item whose performance is unknown, so that I can still track its price.
21. As an inference operator, I want a structured summary of a runtime's backends, formats and work modes, so that I can check whether it suits my stack.
22. As a buyer, I want an overview of at most seven popular, relevant runtimes, so that I can quickly see tradeoffs and evidenced performance.
23. As an inference operator, I want to choose two to five runtimes for a comparison, so that I can focus on the frameworks I might run.
24. As a reader, I want runtime rankings tied to a reproducible workload, so that differences in context, devices or precision are visible.
25. As a builder, I want the same GPU comparison charts on the catalog and card pages with the selected GPU labeled, so that I can see where a card sits.
26. As a chart reader, I want legible, labeled axes and a hover or focus popup with both coordinates, so that I can read exact values.
27. As a chart reader, I want a toggle for point labels and a table with exact values, so that I can inspect dense charts.
28. As a buyer, I want DGX products, AMD AI PCs and other vendor systems in Machines, so that I can compare integrated systems with DIY and creator builds.
29. As a buyer, I want both Machines navigation entries to open the same list, so that I can find a build either way.
30. As a builder, I want original photos or credited publisher thumbnails on build profiles, so that I can inspect the source and recognize the build.
31. As a reviewer, I want machine leads from YouTube, X, GitHub and local AI communities, so that the catalog grows beyond manufacturer examples.
32. As a visitor, I want one to five evidence-backed strengths and limitations on GPU, machine, model and runtime profiles, so that I can quickly judge suitable use cases.
33. As a developer, I want an **awesome-local-llm** wiki, so that I can find inference engines, small models, GPU resources and card-specific tuning references.
34. As a returning visitor, I want a single public brand and durable deep links, so that I can find the same profiles at localdecode.com.
35. As an agent, I want the same IDs, claims, dates and source locators as the HTML reader, so that I can cite a durable answer.
36. As a chart reader, I want to zoom into a crowded section of any chart and restore its full range, so that I can inspect points and labels without losing context.
37. As a keyboard or touch user, I want accessible controls for zoom and reset, so that I can inspect the same region on my device.
38. As a shopper, I want the Costs and Price Watch plots, labels and controls to fit within their own panels, so that overlapping content does not obscure values or selection.
39. As a buyer, I want the GPU I opened to stand out in every GPU profile chart that includes it, so that I can find it immediately at any zoom level.
40. As a buyer, I want the GPU profile to show real photos and useful comparisons without a generic schematic, so that the available space goes to evidence about that card.
41. As a photo researcher, I want to check exact GPU listings and variants on Amazon and eBay, so that I can find additional views and trace them to their original sources.

## Implementation Decisions

### Card photography

- Use the versioned catalog inventory as the denominator. The minimum is one real, release-approved photo for each physical GPU card identity, including stock, board-partner, regional, mining and modified variants. Where the catalog identity denotes a module, distinguish the exact module from a PCIe card. Target multiple distinct views where they show useful details, starting with the face, rear and connectors. A named board-partner example can represent a family-level record when the caption identifies the exact board shown. Exact variants require evidence at that variant's scope.
- Maintain a research ledger by card ID. Search manufacturer and board-partner product pages and press assets, Wikipedia references that lead to Wikimedia file pages, Commons, other open image collections and repos, photographer and creator originals, Google Images and Pinterest. Use SKU, part number, VRAM configuration, PCB and cooler terms for ambiguous or modified cards. Follow aggregator thumbnails, Pins and search hits to the original file page and publisher. Record query scope and review date. Official press art and any alternate type of image stay labeled according to what they depict.
- Keep the displayed asset, captured source revision, precise subject, file or publisher locator, original photo date when documented, publication date, retrieval date, creator or owner, license/permission, dimensions, content digest, meaningful crop or resize, caption and alt text together. A grant must support the intended display, storage, adaptation and redistribution paths. Prefer high-resolution official photos when the publisher grant covers the use, then open-licensed photos and submitted originals with applicable permission. Preserve required credits and share-alike terms.
- Verify exact variants against labels, SKU documents or the original build or modification evidence. GPU, board revision, connector arrangement and memory capacity require separate claims when the photo alone cannot establish them. Evidence from a modification seller stays attributed to that seller. A stock-card photo remains eligible as labeled context on a related record, with its separate identity and coverage status. Reuse a single asset across overlapping identities only when each association independently matches the evidenced subject, such as an exact board and its labeled example on a family record.
- Reuse the catalog media registry, PostgreSQL snapshot and shared HTML and Markdown profile renderers. Publish usable sizes from approved inputs. Retain separate states for published photo, reusable candidate awaiting release review, exact source link only, uncertain match and no reliable source. A gallery link, topic thumbnail, illustration or generic family render carries its own label and contributes zero to exact-photo coverage. Existing profiles continue to show their available evidence while gaps are sourced. Every newly published release reports the denominator, count of exact approved photos and list of missing identities. Completion requires coverage across that entire denominator without placeholder photos. Prioritize unresolved physical cards and obtain original opt-in photos when a publicly reusable source is unavailable.
- Add Amazon and eBay to GPU photo sourcing. Match Amazon ASIN and variation, or eBay item ID and variant, to the exact catalog identity and board part number. Distinguish seller photographs of a specific specimen from reused product imagery. Approved live listing images belong to the related listing and use the provider's display, linking, refresh and removal rules. Amazon's current Associates policy allows caching an eligible image link up to 24 hours and excludes storage of the program image bytes. eBay's API license conditions public listing display on freshness and removal when the listing content is no longer public. Keep these live listing references out of static releases and the permanent GPU gallery unless an independent permission covers durable reuse. Count only cleared, exact photos toward permanent coverage. [Amazon Creators API images](https://affiliate-program.amazon.com/creatorsapi/docs/en-us/api-reference/resources/images) · [Amazon Associates policies](https://affiliate-program.amazon.com/help/operating/policies) · [eBay Browse API](https://developer.ebay.com/api-docs/buy/browse/resources/item/methods/getItem) · [eBay API license](https://developer.ebay.com/support/api-license-agreement)
- Apply the catalog withdrawal policy to withdrawn media. Preserve the provenance and disposition in the editor ledger and rebuild the release projection, linked media and discovery as applicable. A replacement photo retains its own credit and revision.

### Daily used prices and evidence dates

- Research eBay Browse for current listing types, Amazon Creators API for eligible product offers and JD.com Union/Paipai for eligible SKU and secondhand coverage. Verify source-specific access, permitted retention, display, historical derivatives and refresh limits before enabling jobs. eBay sold-data access is a separate decision from current listings. A provider's general catalog or listing page leaves its used-feed coverage unverified. The source register should record a decision and working path or a specific access gap for all three markets/providers. [eBay Buy APIs](https://developer.ebay.com/api-docs/buy/buy-overview.html) · [eBay conditions and sold filters](https://developer.ebay.com/api-docs/buy/static/ref-buy-browse-filters.html) · [Amazon Creators API search](https://affiliate-program.amazon.com/creatorsapi/docs/en-us/api-reference/operations/search-items) · [JD Union APIs](https://jos.jd.com/jdunion) · [JD used graphics cards](https://www.jd.com/hprm/137657d33dda288d1b3a5.html)
- Use the existing regional-price refresher and reviewed PostgreSQL release workflow. Schedule each authorized feed daily in its declared market timezone, with source revision, run status, throttling, retry limits, cursors, freshness and gaps. Preserve stable seller/listing IDs, revision, condition including used/refurbished subtype, identity, market, delivery terms, original currency and precision, taxes and shipping where known, source locator and availability. Keep asking price, bids, completed sales and historical citations separate, with comparable aggregates scoped to approval and equivalent definitions. A partial or failed refresh leaves earlier observations and the gap visible. End-to-end acceptance includes actual daily captures for the requested providers when their verified access and use permit it. Track any outstanding providers as incomplete.
- Treat origin date as field-level evidence. For benchmarks, capture when the run ran. For releases, distinguish announcement, availability and date of the exact revision. For builds, store the disclosed assembly or test date where available. For price, distinguish offer or transaction time from observation and capture. For media, distinguish the actual photo date where disclosed. Keep publisher publication time, revision time and ingestion time separate across all surfaces. Preserve precision and timezone where available, including date-only and unknown. Never infer the origin of a measurement from the publication timestamp.
- Plot Price Watch price on the horizontal axis and measured performance on the vertical axis with visible units and cohort. Use comparable prices under the same market, condition and delivery basis. A point needs an exact scope and released matching measurement. Whole-build cost and performance stay scoped to builds, and single-card quotes join only compatible single-card measurements. Selecting a plotted GPU or build switches its dated price-history chart and accessible table below. Keep history selection available for prices without eligible matching performance. Preserve original currency and independent display conversion.

### Runtime, build and profile comparisons

- Reuse runtime profiles and add structured, source-linked fields for version, backend/driver/platform, supported artifact and quantization formats, workload modes and tested configuration, context/cache/concurrency, hardware scope and source dates. Preserve the full indexed catalog. Use a disclosed, versioned popularity signal or reviewed shortlist to select at most seven for the overview. Rank within one explicit measured workload slice and show evidence, date, scope and ties. Show best observed eligible performance for each chosen runtime in that slice. Keep missing results visible. Keep adjustable workload, metric and other comparison filters distinct from the popularity rule.
- Offer a shareable custom comparison of two to five runtimes from the directory with an explainable limit and keyboard support. Compare workload outcomes and structured capability fields. Link exact runtime and benchmark revisions. Unavailable or incompatible fields get an explicit state. Label tuning claims with source, runtime and card scope. Measured gains require suitable matching evidence. Keep the wiki named **awesome-local-llm** with grouped inference engine, small model, GPU and tuning repositories and exact source links.
- Expand the shared Machines directory for verified DGX, AMD AI PC and other vendor configurations and real creator builds. Keep build and component records distinct. Source creator builds from authorized YouTube, X, GitHub and local inference community disclosures. Keep versioned parts and topology and machine links as data grows. Prefer at least one credited, reusable build photo and more distinct views where available. A YouTube build can use the publisher thumbnail or up to three permitted screenshots from the source, labeled for the actual subject. Both Machines entries route to the same directory and each row opens its exact profile.
- Reuse the shared chart component for GPU, model, machine, runtime and price comparisons. Give memory, speed and bandwidth the correct evidence scope and units. Keep current-card highlighting and linked selection when moving across related plots. Support pointer and focus detail with X and Y values, explicit axis labels, readable ticks, point label toggles and exact tables. Leave missing measurements visible without using a vendor rating or an estimate as observed performance.
- Support zoom on every interactive chart. Give each chart independent, visible zoom and reset controls, with keyboard and touch access. Zoom continuous axes to an inspectable domain and categorical axes to an inspectable subset. Preserve exact values, axis units, linked selection, point label preference and the full-data reset. Panning or zooming one chart preserves the range of neighboring charts. Keep the exact-value table available at any zoom level.
- Fix the overlapping layouts in Costs and Price Watch. Give each plot, its axes, legends, annotations and controls space within its own panel at the supported widths. Apply collision handling to dense marks and labels so their tooltips remain usable. In Price Watch, verify the overview and selected history stay visually separate when a point is selected, labels are enabled or either plot is zoomed. In Costs, give all scenario, cumulative and sensitivity charts the same containment behavior.
- Remove the conceptual schematic and the caption “Original schematic · conceptual GPU and memory layout” from GPU profile pages. Emphasize the current card consistently in each applicable profile chart with the shared selected styling, using orange where it meets contrast requirements. Add a visible label or marker shape as well, so the highlighted card is recognizable without color. Preserve this emphasis through zoom and comparison filtering whenever the card is in the visible domain.
- Place one to five concise strengths and one to five limitations on each card, machine build, model and inference engine profile. Connect each point to its underlying specs, measurements or documented compatibility and to a meaningful use case. Version editorial text and review any generated suggestions. When evidence is incomplete, explain the limitation and its impact with a source or the exact evidence gap.

### Public name and rollout

- Use **localdecode.com** as the displayed site name throughout navigation, logo text, titles, metadata, wiki, discovery and generated public content. Preserve durable URLs, catalog IDs and data ownership. Configure **fastest.ai** as an alternate entry that goes to the same canonical site and preserves deep links. Release the canonical identity and alias behavior together so alternate traffic resolves consistently. An audience-specific second site can be decided separately.
- Deliver in four independently verifiable increments. **Catalog and brand** covers the all-card photo ledger, galleries, canonical naming and dated provenance. **Market evidence** covers the daily provider decisions, collection and Price Watch. **Comparison depth** covers the runtime overview and custom comparison, shared GPU and runtime chart behavior, expanded builds and linked strengths and limitations. **Release verification** covers full inventory acceptance, media rights corrections, replay, access and matching HTML, Markdown and typed results. Keep partial work visible without labeling any incomplete requirement complete.

## Testing Decisions

- Test externally visible behavior from the existing catalog release test seam. Reimport a pinned PostgreSQL snapshot and compare known, representative HTML, Markdown and typed catalog outputs. Audit every GPU identity and require a genuinely matching publishable image before the all-card coverage gate passes. Include stock versus modified, memory variants, module versus PCIe, and similarly named boards. Check required image credit, license and caption, edit notation, responsive image loading and the photo coverage state.
- Replay the same photo data and compare digest and count. Withdraw one asset for a real card and check its displayed profile, list metadata, static exports and public discovery where applicable. Test source approval expiry, duplicate files and a misleading family image. One lost source must leave other approved assets intact and accurately expose any new gap.
- Replay provider inputs through the existing capture and release seam. Exercise used/refurbished cases, unmatched SKU, stale availability, completed versus asking, taxes and shipping unknown, multiple currencies, retry, partial failure and no observations on a scheduled day. Preserve different event, publication and ingestion dates in the table, legend and typed output. Verify provider access and retention decisions against actual captures; fixture data verifies behavior.
- In browser checks, select a Price Watch point and inspect its date-value history and table. Load a price-only SKU manually, update a comparison's currency independently, confirm scope and unit labels and exercise no matching performance. Use the existing chart interaction tests as prior art for hover, focus, touch, label toggles and table parity.
- Add chart interaction and responsive layout regression checks for Costs, Price Watch and representative GPU profiles. Exercise zoom, reset, keyboard and touch controls, dense labels and exact tooltips at wide and narrow widths. Verify axes, legends, point labels and adjoining panels remain legible and contained. Check that the current GPU has a visible, non-color identification in every chart where it appears, remains identifiable when zoomed, and that GPU profiles omit the conceptual schematic and caption.
- Test an exact Amazon variation and eBay listing, an ambiguous shared image, expired display data and a withdrawn or ended listing. Confirm static exports exclude provider images that lack a separate reusable grant. Check the linked listing and permitted refresh limits for live displays.
- Verify the seven-entry runtime cap, two-to-five selection bounds, pinned comparisons, missing comparable trials, popularity provenance, exact backend conditions, ties, source dates and shareable state. Compare the same runtime evidence on overview, custom comparison, profile and export.
- Verify both Machines entries, exact machine details, creator thumbnail scope and accessible source links. Sample the existing Machines, Cards, Models and Runtimes profile sets for guidance counts and check that each statement can be traced to evidence.
- Build the existing Pages review and navigate representative front-door and deep links. Inspect public names, redirects on the configured alias, canonical tags, sitemap, Markdown alternates, social metadata and agent discovery files. Where production cannot be exercised, report the corresponding acceptance gap.

## Out of Scope

- Purchases or commitments to sellers, acquiring new account access as a side effect of the specification, and collection outside a reviewed provider grant.
- Syndicating images with unknown reuse rights, synthetic or illustrative stand-ins counted as real photos, and identifying unpublished board revisions without evidence.
- Independent retesting every catalog card/build/runtime in this release. Controlled benchmark work retains its existing tickets and eligibility requirements.
- A separate fastest.ai application or speculative reordering of existing milestones before their stated acceptance gates are proved.
